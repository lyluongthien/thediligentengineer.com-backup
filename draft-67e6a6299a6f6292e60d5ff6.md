# Understanding PostgreSQL Query Costs: Init Cost vs. Total Cost

PostgreSQL’s query planner uses a cost-based model to determine the most efficient execution plan for a query. Two of the most important metrics reported in the output of the `EXPLAIN` command are the **init cost** (often called **startup cost**) and the **total cost**. In this blog post, we’ll dive deep into what these costs mean, how they are calculated, and how understanding them can help you optimize your queries.

---

## Background: The Cost-Based Optimizer

PostgreSQL uses a cost-based optimizer that evaluates various execution strategies for a given SQL statement. It assigns an estimated cost—measured in arbitrary units—to each operation based on factors such as:

- **Disk I/O:** The cost to read pages from disk (e.g., `seq_page_cost`, `random_page_cost`) [citeturn0search3](https://www.postgresql.org/docs/current/sql-explain.html)
- **CPU Processing:** The cost to process each row (e.g., `cpu_tuple_cost`, `cpu_operator_cost`) [citeturn0search3](https://www.postgresql.org/docs/current/sql-explain.html)

These cost parameters, which you can adjust via configuration (GUC) settings, help the planner predict the “effort” required for each operation. Although the cost units are not direct measures of time (milliseconds), they are comparable across different execution plans.

---

## What Are Init Cost and Total Cost?

When you run an `EXPLAIN` command (or `EXPLAIN ANALYZE`), PostgreSQL outputs a plan that contains two cost numbers for each node in the execution tree:

- **Init Cost (Startup Cost):**  
  The first number represents the cost incurred **before** the node can begin returning rows. Think of it as the “warm-up” cost. For example, a sort operation must read and buffer all its input data before it can start outputting sorted rows [citeturn0search0](https://scalegrid.io/blog/postgres-explain-cost/).

- **Total Cost:**  
  The second number is the overall cost to execute the operation to completion—i.e., to return all rows. It is the sum of the init cost plus the cost of processing all the rows [citeturn0search3](https://www.postgresql.org/docs/current/sql-explain.html).

> **Example:**  
> A node with output `cost=0.00..17.00` means it has a startup cost of 0.00 and a total cost of 17.00. For a sequential scan, this might correspond to reading a set number of disk pages plus processing each row [citeturn0search4](https://stackoverflow.com/questions/117262/what-is-postgresql-explain-telling-me-exactly).

---

## How Are These Costs Calculated?

The planner uses a formula that, in simplified terms, looks like this:

```plaintext
Total Cost = (seq_page_cost × Number_of_Pages) + (cpu_tuple_cost × Number_of_Rows)
```

For operations that require extra processing (like sorting), the startup cost can be significantly higher because the node must complete all preparatory work before returning the first row. In contrast, a sequential scan can often start returning rows immediately (hence a startup cost close to 0) [citeturn0search5](https://dev.to/mghrabi/how-does-postgresql-estimate-the-cost-of-a-query-with-the-explain-command-14lc).

### A Quick Example

Consider the query:

```sql
EXPLAIN SELECT * FROM users LIMIT 1;
```

A typical output might be:

```plaintext
Limit  (cost=0.00..0.02 rows=1 width=17)
  ->  Seq Scan on users  (cost=0.00..17.00 rows=1000 width=17)
```

- **Seq Scan on users:**  
  - *Startup Cost:* 0.00 (it can start reading immediately)  
  - *Total Cost:* 17.00 (to scan the entire table)

- **Limit Node:**  
  - *Startup Cost:* Inherits the child’s startup cost (0.00)  
  - *Total Cost:* Lower overall (0.02) because it stops after fetching one row

This example shows how the LIMIT node benefits from the fact that it does not need to process the entire table, even though the underlying sequential scan has a high total cost [citeturn0search11](https://supabase.com/docs/guides/troubleshooting/understanding-postgresql-explain-output).

---

## Applications in Query Optimization

Understanding these cost metrics is key to effective query tuning:

- **Identifying Bottlenecks:**  
  If a sort operation shows a high startup cost, it means the database must process all rows before output can begin. This might be a target for optimization if you can avoid unnecessary sorting [citeturn0search0](https://scalegrid.io/blog/postgres-explain-cost/).

- **Choosing the Right Indexes:**  
  An index scan generally has lower total cost than a sequential scan when only a few rows are needed. If the EXPLAIN output shows a high total cost on a sequential scan but your query only needs a small subset, consider adding an index [citeturn0search9](https://www.cybertec-postgresql.com/en/how-to-interpret-postgresql-explain-analyze-output/).

- **Evaluating Query Plans:**  
  Comparing the estimated init cost and total cost across different plans helps you understand whether the planner’s choice is optimal. For example, a nested loop join might start returning rows quickly (low init cost) but may incur a higher total cost if the inner loop processes many rows repeatedly [citeturn0search4](https://stackoverflow.com/questions/117262/what-is-postgresql-explain-telling-me-exactly).

## Formula used for PostgreSQL cost calculation
This diagram breaks down the process into retrieving table statistics and cost parameters, then computing the disk and CPU costs, and finally summing them up to produce the total cost.

```mermaid
flowchart TD
  %% Table Statistics
  A[Table Statistics] --> A1[Number of Pages (N_pages)]
  A[Table Statistics] --> A2[Number of Rows (N_tuples)]
  
  %% Cost Parameters
  B[Cost Parameters] --> B1[seq_page_cost<br/>(e.g., 1.0)]
  B[Cost Parameters] --> B2[cpu_tuple_cost<br/>(e.g., 0.01)]
  B[Cost Parameters] --> B3[cpu_operator_cost<br/>(e.g., 0.0025)]

  %% Disk Cost Calculation
  A1 --> C[Compute Disk Cost]
  B1 --> C
  C -->|Formula: N_pages × seq_page_cost| D[Disk Cost]

  %% CPU Cost Calculation
  A2 --> E[Compute CPU Cost]
  B2 --> E
  B3 --> E
  E -->|Formula: N_tuples × (cpu_tuple_cost + cpu_operator_cost)| F[CPU Cost]

  %% Total Cost
  D --> G[Total Cost Calculation]
  F --> G
  G -->|Formula: Disk Cost + CPU Cost| H[Estimated Total Cost]
  
  %% Annotations
  style A fill:#E8F0FE,stroke:#4285F4,stroke-width:2px
  style B fill:#E8F0FE,stroke:#4285F4,stroke-width:2px
  style D fill:#FFF3CD,stroke:#FFC107,stroke-width:2px
  style F fill:#FFF3CD,stroke:#FFC107,stroke-width:2px
  style H fill:#D4EDDA,stroke:#28A745,stroke-width:2px
```

---


1. **Table Statistics (A):**  
   - The database gathers **N_pages** (number of disk pages used by the table) and **N_tuples** (number of rows in the table).

2. **Cost Parameters (B):**  
   - **seq_page_cost (B1):** The cost for reading a sequential page (default is typically 1.0).  
   - **cpu_tuple_cost (B2):** The cost for processing each row (default is often 0.01).  
   - **cpu_operator_cost (B3):** The additional cost for any operators or functions (default around 0.0025).

3. **Disk Cost Calculation (C → D):**  
   - The disk cost is computed by multiplying the number of pages by the sequential page cost:
     \[
     \text{Disk Cost} = N_{\text{pages}} \times \text{seq\_page\_cost}
     \]

4. **CPU Cost Calculation (E → F):**  
   - The CPU cost is computed by multiplying the number of rows by the sum of the per-tuple and per-operator costs:
     \[
     \text{CPU Cost} = N_{\text{tuples}} \times (\text{cpu\_tuple\_cost} + \text{cpu\_operator\_cost})
     \]

5. **Total Cost Calculation (G → H):**  
   - Finally, the total estimated cost is the sum of the disk cost and CPU cost:
     \[
     \text{Total Cost} = \text{Disk Cost} + \text{CPU Cost}
     \]

This detailed diagram visually represents how PostgreSQL calculates query cost estimates using table statistics and configurable cost parameters. Adjusting these parameters can affect the planner’s choice of execution plan, making this knowledge key for performance tuning.

Feel free to modify the values in the diagram to match your environment or add additional nodes if your cost formula includes extra factors.


> **Diagram Explanation:**  
> - **Seq Scan:** Reads the table with a total cost of 17.00 [citeturn0search3](https://www.postgresql.org/docs/current/sql-explain.html).  
> - **Sort:** Must sort all rows before it can output any, hence a high startup cost (66.83) with a total cost of 69.33 [citeturn0search8](https://medium.com/geekculture/how-to-read-and-understand-explain-query-plans-in-postgresql-8179299fd613).  
> - **Limit:** Stops processing after the first row, so its total cost is very low (0.02) despite inheriting the startup cost from the sort [citeturn0search11](https://supabase.com/docs/guides/troubleshooting/understanding-postgresql-explain-output).

## Conclusion

PostgreSQL’s EXPLAIN output provides invaluable insight into how a query is executed. By understanding the **init cost** (startup cost) and **total cost**, you can:
 
- Identify expensive operations (like sorts and joins)
- Determine if your table statistics need updating
- Choose whether adding an index might reduce the overall cost
- Fine-tune queries for better performance

Armed with this knowledge—and using tools like [Depesz’s EXPLAIN visualizer](https://explain.depesz.com/) and [Supabase’s documentation](https://supabase.com/docs/guides/troubleshooting/understanding-postgresql-explain-output)—you can better diagnose performance issues and design more efficient queries for your applications.
